# Gate 3 — RL pipeline (stub dynamics)

Status: the train → save → reload → evaluate path runs end to end (2026-10-25).
The physics and fault modules here are **stubs**: they exist so the RL side can be
built before Gate 1 and Gate 2 are ready. Their numbers are not vehicle data.

## What is in place

| Piece | File | Notes |
|---|---|---|
| 6-DOF rigid body, rotor thrust/torque | `envs/stub_dynamics.py` | NumPy, semi-implicit Euler, 240 Hz |
| Single-rotor failure | `envs/stub_faults.py` | masks one motor after `failure_time_s`; partial effectiveness supported |
| Gymnasium task | `envs/quadrotor_env.py` | implements the Gate 0 observation / action / reward / termination proposal |
| PPO training | `train/train_ppo.py` | SB3 PPO, checkpoint + metadata + CSV logs |
| Deterministic evaluation | `eval/evaluate.py` | reserved eval seeds, metrics, trajectory plot |
| Plots | `eval/plotting.py` | learning curve and evaluation figure |

The dynamics and fault injector sit behind the interfaces in `docs/INTERFACE.md`, so
Andy's and Joe's modules can replace the stubs without touching the training code.

## Environment

Conda env `uav-g3`. **The stack moved on 2026-11-10** (see the migration section
below) and the pins now live in `environment.yml`; the versions the 2026-10-25
numbers below were produced with were Python 3.10.22, numpy 1.26.4, gymnasium
0.29.1, SB3 2.2.1, pandas 2.0.3, matplotlib 3.7.5, pytest 7.4.4, torch 2.0.1+cu117
(user site). The default commands use CPU and set `CUDA_VISIBLE_DEVICES=""` so the
reported numbers are reproducible.

GPU note (tested 2026-10-28): the same torch does run on the RTX 4080 Laptop
(compute capability 8.9, driver 580.178.04 / CUDA 13.0) through CUDA forward
compatibility. A 200,704-step run took 101 s (~2100 fps, about 2× the CPU run) and
20/20 evaluation episodes survived; the final error was 0.515 m versus 0.235 m on the
CPU run. The runs are independent and neither is converged, so the difference is not a
GPU numerical fault. This is still not an officially supported combination: for
long-term stability, install torch 2.4.1+cu121 in a dedicated environment and run with
`PYTHONNOUSERSITE=1` so the user-site torch used by another project is not picked up.
To opt into GPU now, pass `--device cuda` and do not set `CUDA_VISIBLE_DEVICES=""`.

  /home/albertpang/miniconda3/envs/uav-g3/bin/python -m pytest tests -q

  /home/albertpang/miniconda3/envs/uav-g3/bin/python -m train.train_ppo \
  --config configs/g3_hover.yaml

# evaluate a saved policy (no learning)
env -u PYTHONPATH CUDA_VISIBLE_DEVICES="" \
  /home/albertpang/miniconda3/envs/uav-g3/bin/python -m eval.evaluate \

`env -u PYTHONPATH` keeps ROS's Python packages out of the conda interpreter.
Useful overrides: `--timesteps`, `--n-envs`, `--name`, `--device`, `--seed`, and
repeatable `--set path=value` for training; `--episodes`, `--seed-start`, `--out`
for evaluation.

## Comparisons and ablations (2026-11-11)

Changing two numbers used to mean copying a YAML file. Now `--set` writes any
dotted path in the resolved config, and `train/sweep.py` runs a grid:

```bash
# one run, two values changed
python -m train.train_ppo --config configs/g4_fixed_rotor1.yaml \
  --set ppo.n_epochs=5 --set ppo.learning_rate=1.0e-4 --seed 3

# 2 learning rates x 2 seeds, each trained and evaluated
python -m train.sweep --config configs/g4_fixed_rotor1.yaml \
  --grid ppo.learning_rate=1e-4,3e-4 --seeds 0,1 --timesteps 200000
```

`apply_override` in `envs/config.py` parses the value as YAML and **rejects a path
that does not exist**, listing the keys that do. A misspelt ablation arm must not
quietly reproduce the baseline. Overrides are applied before
`validate_structure` and before `--print-config`, so the preview and the
`config_sha256` in `meta.json` both describe the run that actually happens.

A sweep is a sequence of ordinary `train.train_ppo` subprocesses — not a second
implementation — so `unique_run_dir` still protects existing checkpoints. It
writes `plan.json` before starting, appends to `summary.csv` as each run
finishes, and keeps a per-run log. Run names are `<run name>-000`, `-001`, …;
the resolved directory is read back from the child's own `checkpoints:` line, so
a `-002` collision suffix is reported correctly. Evaluation is the same
`eval.evaluate`; `--no-eval` skips it, `--dry-run` prints the plan, and
`--stop-on-error` halts at the first failure.

Two limits worth knowing: grid values are scalars only (commas separate values,
so `net_arch=[64,128]` needs its own config file), and `--set` cannot create a
key that is absent from the config — see the Gate 0 note below for why that is
deliberate.

`tests/test_sweep.py` (15 tests) pins the typing, the unknown-path rejection,
the internal-key rejection, the Cartesian product order, and the fact that
`1e-4` arrives as a float rather than the string PyYAML would produce. Suite
total 89.

## 200k-step nominal run (2026-10-25)

`configs/g3_hover.yaml`: 4 envs, 200,704 steps, 200 s wall clock (~1000 fps CPU).

Deterministic evaluation on 20 unused seeds (100000–100019):

| metric | value |
|---|---|
| episodes reaching the 10 s time limit | 20 / 20 |
| mean return | 566.2 ± 1.7 (max 600) |
| final position error | 0.235 m (max over episodes 0.235 m) |
| position RMSE | 0.219 m |
| crash / out-of-bounds rate | 0 / 0 |

Reading these honestly:

* The policy learned to **survive**, not to hold position tightly. Every episode settles
  at z ≈ 1.171 m and drifts slowly in x/y; the error is a steady bias, not noise.
* The training curve is still rising at the 200k cutoff (last update: mean return 246,
  mean episode length 424 of 600). The budget is too short to call it converged.
* Training returns are lower than evaluation returns because training samples stochastic
  actions (`std ≈ 0.92`) while evaluation uses the deterministic mean.
* The stub parameters (0.5 kg, 2 N per rotor, 0.092 m arm) are placeholders. Do not quote
  these numbers as vehicle performance.

Likely causes of the bias: position-error weight 1.0 is small next to the +1/step alive
reward, and the policy settles wherever its thrust bias balances the penalty. Reward
weights are a team decision — revisit after Gate 0 freeze, and try a longer run before
changing them.

## Added after G3: PyBullet backend (2026-11-10)

Nothing above changed. `dynamics.backend` in the config now selects the
integrator, and the existing paths keep `numpy`:

| `dynamics.backend` | class | file |
|---|---|---|
| `numpy` (default) | `StubDynamics` | `envs/stub_dynamics.py` |
| `pybullet` | `PyBulletDynamics` | `envs/pybullet_dynamics.py` |

`PyBulletDynamics` implements the same `reset` / `step` / `applied_thrusts` /
`hover_command` as the stub, so the environment, observation, reward, fault
injector, training and evaluation are untouched. It builds a cylinder body with
the config's mass and inertia, applies the four rotor forces at their hub
positions and the same yaw reaction torque, and adds what the stub cannot
model: **a ground plane**.

Verification (`tests/test_pybullet_backend.py`, 15 tests; suite total 89 as of
2026-11-11, the extra 15 being the override/sweep tests added below):
with the plane off, the two backends are indistinguishable — 4 s of hover is
bit-for-bit identical, and three sustained-torque cases (yaw, pitch, roll)
drift by at most 0.041 mm over 4 s while the vehicle travels 35 m and tumbles
past 100°. With the plane on they *must* disagree: the stub falls through z = 0,
the engine lands. That is the only intended difference.

Speed is not a reason to hesitate: measured through `QuadrotorEnv`, 500 control
steps after warm-up, **numpy 1755 steps/s (0.57 ms/step) vs pybullet 3078 steps/s
(0.32 ms/step)** — the engine is *faster* than the stub.

Known modelling gap: pybullet's `linearDamping` is a decay rate (1/s), not our
force-per-speed coefficient (N/(m/s)). The engine's damping is therefore set to
zero and the drag terms are applied as explicit forces, exactly as the stub does.
Do not "simplify" this back into `changeDynamics`.

## Added after G3: the task now runs on gym-pybullet-drones (2026-11-10)

The supervisor asked for the work to stand on gym-pybullet-drones rather than on
code we wrote ourselves, so the task moved onto it. `env.impl` in the config
selects the implementation; the two earlier ones stay runnable:

| `env.impl` | class | vehicle |
|---|---|---|
| `gpd` (**default** from this date) | `GPDQuadrotorEnv`, `envs/gpd_env.py` | gpd `cf2x` URDF |
| `legacy` + `dynamics.backend: numpy` | `QuadrotorEnv`, `envs/quadrotor_env.py` | `dynamics.*` in the config |
| `legacy` + `dynamics.backend: pybullet` | `QuadrotorEnv`, `envs/quadrotor_env.py` | `dynamics.*` in the config |

`GPDQuadrotorEnv` subclasses `BaseAviary` from the vendored package in
`third_party/` (commit `348b5c1`, MIT, see `third_party/NOTICE.md`). The world,
URDF, force mapping, physics stepping and GUI are gpd's; the observation layout,
reward, termination, fault injection, scenario sampling and seeding are ours and
unchanged. `envs/env_factory.py` builds whichever the config names.

**The vehicle changed, and that is the headline.** gpd's `cf2x` is 0.027 kg with
a 0.0397 m arm, thrust-to-weight 2.25, and thrust quadratic in the normalised
command (`KF · rpm²`). The stub airframe in `configs/*.yaml` is 0.5 kg, arm
0.092 m, T/W 1.63, thrust linear. So **none of the G3 numbers above were
re-measured on the new machine** — they remain the legacy implementation's, and a
`gpd` comparison needs a fresh training run. A checkpoint is evaluated on the
implementation recorded in its `meta.json`, so old runs still reproduce exactly.

### What was verified, not assumed

* `tests/test_gpd_env.py` (11 new tests) — rotor permutation, fault timing, hover
  holding altitude open-loop, a failed rotor actually losing thrust, the
  fault-unaware rule, and the factory switch. Suite total 74 at that point, all passing.
* **Rotor order.** gpd's URDF numbers its links FR, RR, RL, FL; ours are FR, FL,
  RL, RR. `ROTOR_GPD_INDEX = (0, 3, 2, 1)` in `envs/gpd_env.py` and every command
  is permuted through it. This was found the hard way: the mapping was defined
  but not applied, which is invisible at hover (all four motors equal) and
  silently failed rotor 3 when the scenario said "rotor 1". The test now fails
  each rotor in turn and checks the sign of the resulting roll and pitch rates
  against the geometry.
* **Action-rate penalty.** `BaseAviary.step` calls `_preprocessAction()` *before*
  `_computeReward()`, so storing `_prev_action` there made `||u_t − u_{t−1}||²`
  identically zero — a reward term silently absent from every run. The difference
  is now measured before the update and pinned by a test.
* **Two OpenMP runtimes.** With torch imported, the first `numpy.linalg` call on
  Windows aborts the process ("Fatal Python error: Aborted", top frame in LAPACK,
  no traceback). It only appeared when the *whole* suite ran, because collection
  imports torch before any test. Every entry point now sets
  `KMP_DUPLICATE_LIB_OK=TRUE` before importing torch.
* `tools/crosscheck_gpd.py` puts the three implementations side by side. All three
  hold altitude at their own hover command and apply the thrust they report
  (residual 0.06 % legacy, 0.29 % gpd). Cost per control step: **gpd 0.17 ms**,
  PyBulletDynamics 0.34 ms, StubDynamics 0.47 ms.

### What changed around the code

* `environment.yml` — Python 3.12.16, numpy 2.5.4, scipy 1.18.1, gymnasium 1.3.0,
  SB3 2.9.2, torch 2.15.0+cpu, and **pybullet from conda-forge** (PyPI ships no
  Windows wheel; conda-forge calls it 3.25, the package is 3.2.5).
* `eval/evaluate.py`, `eval/fault_response.py`, `eval/replay.py` build the env
  through `envs.env_factory.make_env`, so they evaluate a checkpoint on the
  implementation it was trained with. `fault_response` reads the vehicle through
  the env (`hover_action`, `applied_thrusts`, `mass_kg`) instead of reaching into
  `env.dynamics`, and `replay` draws the airframe the episode was flown on.
* `validate_structure(..., expect_resolved=True)` no longer demands `dynamics.*`
  for `env.impl: gpd` — that implementation reads the URDF. The legacy path is
  still refused when the vehicle parameters are null.
* The upstream examples run from the vendored copy on the project environment.
  Twelve menu entries (`--run gpd_pid`, `gpd_hover`, `gpd_pid_velocity`,
  `gpd_mrac`, `gpd_downwash`, `gpd_pettingzoo`, `gpd_debug`, `gpd_learn_small`,
  `gpd_learn_full`, `gpd_play`, `gpd_tests`, plus `gpd_beta` behind a guard)
  run `gym_pybullet_drones.examples.*` with `PYTHONPATH=third_party/`, each with
  its own log folder under `.scratch/gpd_example_results/` so nothing can be
  mistaken for our results. Verified on Windows 11, one run each, exit 0 —
  except that `gpd_play` ends only when its matplotlib window is closed
  (upstream's own behaviour) and `gpd_beta` refuses until Betaflight SITL is
  compiled. Three upstream scripts are called as `run(**kwargs)` instead of
  through their CLI because their argparse is missing the option that matters
  (`mrac` has no CLI at all, `downwash` has no `--plot` while defaulting it to
  True, `pettingzoo_multiagent` defaults to 1e6 training steps); the comments in
  `run.py` say which and why.
* `tools/gpd_demo.py` sits between `run.py` and the vendored examples and fixes
  two upstream nuisances. (a) **GUI text was clipped**: pybullet's default
  `OpenGL3+ [btgl]` window draws every label one character left of its clip
  rectangle (`File`→`rile`, `Explorer`→`xplorer`, `Params`→`arams`). Declaring
  DPI awareness (2560×1440 at 125 %) and enlarging the window to 1600×900 both
  left it unchanged, so it is the renderer, not the desktop. The legacy
  `--opengl2` renderer draws the text whole, at the cost of shadows, floor
  textures and the ball texture; it is off by default and `UAV_GPD_GL=2` turns
  it on. Since
  `BaseAviary` hard-codes `p.connect(p.GUI)`, the options are injected by
  wrapping `pybullet.connect`. (b) **Demos stopped on their own**: upstream
  hard-codes 5–15 s (`pid.py`: `DEFAULT_DURATION_SEC = 12`), which reads as a
  timer. The menu passes `--duration_sec`/`duration_sec` explicitly —
  `UAV_GPD_DURATION_SEC`, default 60 s. Legacy-renderer windows also come up
  minimised here, so the wrapper restores them with `ShowWindow`.
* **Upstream's own test suite passes here**: 13 passed in 55 s
  (`--run gpd_tests`), against the vendored copy, provided `torch` is imported
  *before* pytest starts. Without that pre-import, on Windows two of the
  thirteen fail with `WinError 127` loading `torch\lib\shm.dll`: the earlier
  examples leave MKL's `libiomp5md.dll` loaded, and torch's identically-named
  DLL then cannot be mapped. It is a load-order problem, not a version problem.
* These examples bypass our task, reward and fault logic: they are a demo, not a
  verification of anything we claim. `pettingzoo` and `control` are in
  `environment.yml` only so that `gpd_tests` and `gpd_mrac` work on a fresh
  environment.
